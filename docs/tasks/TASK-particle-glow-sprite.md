# TASK: Replace ParticleText's per-draw shadow blur with pre-rendered sprites

> **Built, measured, reverted — the change made performance significantly worse.** Kept as a
> record so the idea isn't re-attempted from scratch: it is the obvious optimization here and
> it does not work. Results at the bottom.
>
> Split out of `TASK-frame-budget-cleanup.md`, which measured the problem but could not fix it
> under its own "zero visual change" contract.

## Current scenario

`TASK-frame-budget-cleanup.md` reduced frames over 33ms at 6x CPU throttle from 9.7% to 5.4%,
short of its estimate. Re-profiling after that work found the same canvas function still at
12.0% of main-thread self-time with native `fill` at 4.1% — the batching helped less than
expected because the cost is **rasterization, not canvas state**.

The specific mechanism is `ParticleText`'s glow. `particle-text.tsx:255-260` sets:

```ts
ctx.shadowBlur = particleSize * 3;
ctx.shadowColor = highlightColor;
```

once per frame, and every particle is then drawn through it. A canvas shadow is not a cheap
state flag — each draw call renders the shape, blurs it into a scratch surface, and composites
the result. The homepage's Hero mounts **two** `ParticleText` instances, and at
`particleSize: 2.6` every particle takes the `arc()` + `fill()` path rather than the cheap
`fillRect` branch at `particle-text.tsx:243`, so the blur runs per particle per instance per
frame.

Two properties of this component make the fix straightforward:

- **Every particle's glow is the same colour.** `shadowColor` is `highlightColor`, fixed,
  regardless of the particle's own colour.
- **Particle colours lie on one axis.** `particle-text.tsx:431-434` computes
  `mixRgb(baseRgb, highlightRgb, blend)` with `blend` clamped to 0–1, so the whole palette is
  a single gradient, and sizes are `particleSize * (0.75 + alpha * 0.45)` — a narrow range.

Both quantize without being noticeable at 2–4px.

## Planned changes

### `src/components/react-bits/particle-text.tsx`

Build a small sprite atlas once, after particles are sampled, and replace the per-particle
shadow draw with a single `drawImage`.

- **12 blend levels x 4 size buckets = 48 offscreen canvases**, each roughly 20x20px. Built by
  drawing the particle exactly the way the current code does — `arc()` + `fill()` with
  `shadowBlur`/`shadowColor` set — so each sprite *is* the current rendering, just computed
  once instead of every frame.
- Sprites are built at a fixed geometry per size bucket rather than one sprite scaled per
  particle. Scaling a single sprite would scale the glow with the core, but `shadowBlur` is
  currently constant across particle sizes, so a scaled sprite would render a visibly
  different falloff on small particles. Bucketing keeps the blur constant, which is what the
  current code does.
- The draw path becomes `ctx.drawImage(sprite, x - w/2, y - h/2)` at natural size: no scaling,
  no state change, no blur pass. `globalAlpha` still varies per particle for the gather
  animation and is unaffected.
- **The existing non-glow path stays exactly as it is.** When `glow` is false or
  `prefers-reduced-motion` is set, nothing changes — no sprites are built and the original
  `fillRect`/`arc` branch runs.
- Rebuild the atlas whenever the inputs change (`particleSize`, `color`, `highlightColor`,
  device pixel ratio), alongside the existing resample triggers.

This stays a vendored React Bits component (`TASK-react-bits-mcp-registry.md`), so the change
is marked with the same `BLESSED MOON:` comments used for the frame-loop migration, and the
upstream code path is preserved rather than deleted.

## Why

It is the largest remaining main-thread cost on the homepage after Tier 1, and unlike the moon
(which Tier 2 relocates rather than reduces) it is pure waste: the same handful of small
images are being re-blurred from scratch sixty times a second.

The visual result should be indistinguishable — the sprites are generated by the current
drawing code — but it is an approximation in two places, and both are judgement calls rather
than facts: colour is quantized to 12 steps along a gradient, and size to 4 buckets. **This
needs a before/after capture reviewed before it is accepted**, which is the reason it was kept
out of the zero-visual-change tier rather than folded into it.

Cost: ~48 small canvases held for the life of the component (negligible memory, but it is
state that did not exist before), and a rebuild step tied to prop changes that must not be
missed — a stale atlas would render the wrong colours after a prop update.

## Outcome — reverted

Implemented as described (12 blend levels x 4 size buckets, built with the component's own
`arc()` + `shadowBlur` code, drawn with `drawImage` at natural size), then profiled at 6x CPU
throttle against the Tier 1 build:

| @6x CPU | Tier 1 | Tier 1 + sprites |
|---|---|---|
| mean fps | 51.3 | **43.9** |
| frames >33ms | 5.4% | **13.5%** |
| worst frame | 67ms | **516ms** |

`drawImage` became 17.3% of main-thread self-time — more than the `shadowBlur` path it
replaced. (These are single runs, and single runs on this page are unreliable — but the effect
is far larger than the ±1.5pp run-to-run spread, so the direction is not in doubt.)

**Why it lost.** The reasoning was that a blur pass per particle per frame must cost more than
a blit. It does — but the blit isn't small. `shadowBlur` is `particleSize * 3`, so at
`particleSize: 2.6` each sprite has to be about 22x22 CSS px to contain the glow's falloff.
Blitting a 22x22 RGBA image with `globalAlpha` for every particle, across two `ParticleText`
instances, moves far more blended pixels than the browser's shadow implementation does — it
appears to rasterize only the meaningful alpha region, while the sprite pays for its whole
bounding box including the almost-transparent margin.

The 516ms worst frame is the atlas build: 48 canvases, each drawn with a real `shadowBlur`,
constructed in one synchronous pass during sampling.

**What would have to be different** for this to be worth revisiting: a materially smaller glow
radius (a visual change to the design, not an optimization), or a single instanced WebGL draw
for the whole particle field instead of per-particle Canvas2D — which is a different task, and
a much larger one, best considered alongside `TASK-ascii-offscreen-worker.md` since it would
mean a second GL context.
