# TASK: React Bits shadcn registry + MCP server

## Current scenario

`components.json` already declares one custom shadcn registry, `@canvas-ui`
(`https://canvasui.dev/r/{name}.json`), used to pull in AsciiObject, ParticleObject,
ParticleScroll, DecryptReveal (`TASK-ascii-canvas-layer.md`). There is no `@react-bits`
registry entry and no shadcn MCP server configured for this repo (no `.mcp.json`).

## Planned changes

1. Add a second registry entry to `components.json`'s `registries` block:
   `"@react-bits": "https://reactbits.dev/r/{name}.json"`, alongside the existing
   `@canvas-ui` entry — additive, no removal.
2. Run `pnpm dlx shadcn@latest mcp init --client claude` to generate/update the Claude
   Code MCP server config for the shadcn CLI (project uses pnpm exclusively per §4, not
   npx, even though React Bits' own docs show `npx`).
3. No component is being installed yet — this task only wires up the registry + MCP
   server so React Bits components can be browsed/added via natural-language prompts in
   a later task, per this repo's use-tooling-not-hand-rolled-markup convention (§2).

Alternative considered: skip the MCP server and just add the registry entry, using
`pnpm dlx shadcn@latest add @react-bits/<name>` manually per component. Rejected — the
user explicitly asked for the MCP server setup, which is what enables the natural-language
browse/install flow the React Bits docs describe.

## Why

Requested by the user, who pasted React Bits' MCP setup docs and confirmed (via
clarifying question) they want the registry + MCP server configured now, ahead of any
specific component being added. This unblocks future frontend work — additional
scroll/background effects — without hand-rolling animation code that a maintained
component library already covers, consistent with §2's "don't hand-roll what a
generator/registry produces."
